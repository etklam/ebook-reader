# RV-009｜括號編號以外的分段標記仍會令整本變成一章

- 嚴重度：高
- 優先級：P1
- 工作量：中
- 類型：AFK
- 狀態：implemented-local（2026-10-24）

## 要做的事

`a70e306` 修好了 `（一）`／`(1)`／`（１）` 這一組寫法，但同一個失敗模式對其他常見編號標記依然成立：整個檔案變成一個十幾萬字的章節。本票要處理這一類標記，並補上使這類回歸可被偵測的測試。

## 分析

### 實測結果

以 `server/src/import/txt-parser.ts` 的 `parseTxt()` 直接驗證，每個樣本都是「三行一節、節與節之間空行」的標準結構：

| 來源寫法 | 結果 | 說明 |
| --- | --- | --- |
| `（一）` `（二）` | 正確分章 | `a70e306` 覆蓋 |
| `(1)` `(2)` | 正確分章 | `a70e306` 覆蓋 |
| `（１）` `（２）` | 正確分章 | `a70e306` 覆蓋 |
| `（一)` `（二)`（全角開、半角閉） | **整本一章** | 括號不同寬度 |
| `(一）` `(二）` | **整本一章** | 同上，反向 |
| `（ 一 ）` `（ 二 ）` | **整本一章** | 括號內有空白 |
| `【一】` `【二】` | **整本一章** | 方頭括號 |
| `〔一〕` `〔二〕` | **整本一章** | 六角括號 |
| `一、` `二、` | **整本一章** | 頓號編號 |
| `其一` `其二` | **整本一章** | 文言序數 |

所有「整本一章」的個案，`warnings` 都是 `['no_reliable_chapter_boundaries']`，正文長度等於整個檔案 —— 與 `a70e306` 的 commit message 描述的原始症狀（「the importer saw a single 180,000-character chapter」）完全一致。

### 為何是一章而不是部分分錯

`txt-parser.ts` 有兩層標題偵測：

1. `looksLikeMarkerHeading()`（`:53-62`）比對 `HEADING_RE`（`:31-39`）。括號編號那一支是 `:36`：`（[0-9０-９零〇一二三四五六七八九十百千两兩]+）|\([…]+\)` —— 要求左右括號**同寬度**、中間**只有**該字元類內的字元（所以空白、`廿`、`卅` 都不符），而 `【】`、`〔〕`、`一、`、`其一` 完全不在任何一支之內。
2. `looksLikeBareTitle()`（`:67-70`）是寬鬆的 fallback：短、獨立、不以句末標點結尾的一行就算標題。

關鍵在第 2 層的開關：`:113` 的條件是 `sawMarkerHeading && prevBlank && …`。`sawMarkerHeading` 只有在第 1 層命中過一次之後才會變 `true`（`:106`）。所以一份**全書都用 `【一】` 編號、完全沒有 `第…章`** 的來源，第 1 層永不命中 → 第 2 層永不啟用 → 全部行落入同一個 `current.paraLines` → 一章。

這解釋了一個反直覺的觀察：同樣的 `【二】`，只要檔案前面有任何一行 `第一章`，就會被正確切開（實測確認）。失敗與否取決於檔案裡有沒有一個「已知寫法」去啟動 fallback，而不是取決於 `【二】` 本身。

### 兩個附帶問題

**(a) 標題相符但無編號 key。** `（廿一）` 會被第 2 層切開（因為前面的 `（二十）` 已啟動 fallback），但 `parseLabel('（廿一）')` 回傳 `kind: 'unnumbered'`、`key: null` —— `廿` 不在 `parse-label.ts:132` 的字元類內。`【二】`、`二、`、`〔二〕`、`其二` 同樣是 `key: null`。後果見 `parse-label.ts:10-12` 的契約：「Unparseable numbering yields numbered: null — matching just falls back to title/body evidence」。即首次匯入看似正常，但之後重新匯入同一本書（RV-011）時無法按編號匹配既有章節，會被當成整批新章插入。

**(b) 散文中的列舉會被誤判成標題。** 實測 `第一章\n前文\n（二）這是正文列舉\n後文\n` 得到 **2 章** —— `（二）這是正文列舉` 被當成章節標題。`a70e306` 的 commit message 聲稱這種情況「stays content」，但實際上只因為它舉的例子結尾有句號，被 `:60` 的 `SENTENCE_END` 擋住。沒有句末標點的列舉行會變成假章節。注意 `:105` 的 marker 分支**沒有**檢查 `prevBlank`，所以緊貼在正文中間的一行也可以成為標題；只有第 2 層的 bare title 才要求前面有空行。

### 修正方向

不建議無限擴充 `HEADING_RE` 的字面列表 —— 每加一種寫法就是下一張同樣的票。三個可組合的方向：

- **A（核心）**：把括號編號一支一般化：左右括號各自接受 `（(【〔[`／`）)】〕]` 任一，允許括號內有空白，數字部分擴充 `廿卅`。同時把「開閉括號必須配對」作為明確規則（不接受 `（二]`）。
- **B（解決根因）**：放寬第 2 層的啟用條件。目前 `sawMarkerHeading` 是個全有全無的開關；改為「文件層面偵測一致的編號模式」：掃一遍全檔，若有 ≥N 行（例如 3 行）符合同一個「短、獨立、以序數開頭」的形狀，就以該形狀作為本檔的章節標記。這樣 `一、`、`其一`、任何未預見的寫法都會自己被認出，而不需要列舉。代價是需要明確的信心門檻與 `needsReview` 標記。
- **C（防誤判）**：令 marker 分支也要求 `prevBlank`（與 bare title 一致），修掉 (b)。需確認不會令現有 `第…章` 緊貼正文的來源回歸 —— `txt-parser.test.ts` 應該已有相關 case，實作時必須先確認。

建議 A + C 先行（範圍明確、可驗證），B 另行評估，因為它改變了「不確定時寧願不切」這個已有的保守取向，需要在 `needsReview` 與匯入覆核流程（ER-010）上配套。

另須注意：`parse-label.ts` 與 `m0/label-parser/parse-label.ts` 目前是逐字相同的（已以 diff 確認），`a70e306` 亦明言兩份要一起改。本票任何 `parse-label` 的改動必須同步兩份。`HEADING_RE` 只存在於 `server/src/import/txt-parser.ts`，m0 沒有對應檔案。

## 實作結果（2026-10-24）

採用的方案不是「擴充字面列表」（方向 A）也不是單純放寬 fallback（方向 B），而是兩者的結合：**放寬辨識範圍，再用文件層一致性作為安全閘**。

1. 括號編號那一支從 `HEADING_RE` 移走。`HEADING_RE` 現在只保留本身無歧義的強形式（`第N章` 家族、序／終章、番外），一次出現即可信。
2. 新增 `WEAK_FORMS`：`（N）`／`(N)`（全半角可混用）、`【N】`、`〔N〕`、`其N`、`N、`，皆容許括號內空白，數字擴充 `廿`／`卅`。
3. 新增 `weakHeadings()`：對**整份文件**逐一形式掃描，取出數字嚴格遞增的最長序列，只有在至少兩項存活時才承認該形式。這一條同時達成兩件事 —— 完全沒有其他標記的 `【一】【二】【三】` 文件得以分章，而 `第一章` 文件裡孤零零一行 `（二）這是正文列舉` 因為只有一次出現而被判為內文。
4. 被序列檢查否決的行會記入同一個 map（值為 `null`），主迴圈據此令它**不能**再落入 `looksLikeBareTitle` 的寬鬆 fallback。這是實作中發現的必要修正：否則剛被判定為列舉的一行會被較寬鬆的規則重新提升成標題。
5. `N、` 額外要求前面有空行。`一、` 本身比括號形式弱得多（`他說三、四月間的事` 是正常句子），而括號形式不加這個要求，因為許多來源的標題緊貼上一段、中間沒有空行。
6. 提供 `chapterPattern` 時完全不啟用弱形式猜測 —— 管理員已經明示規則。

`parseLabel` 同步擴充：括號三類（不接受交叉配對如 `（二】`）、`N、`、`其N`、`廿`／`卅`。兩份 parser 的一致性由新測試 `the M0 reference parser and the running parser stay identical` 強制，並已以人工製造漂移驗證該測試會失敗。

驗證：`pnpm lint`、`pnpm typecheck` 乾淨；server 測試由 137 增至 146 項全過，既有 case 無一需要改變預期。未執行：以真實使用者來源檔案的現場匯入（`m0/fixtures/txt/` 的 base-180、full-190、weird-labels 已覆蓋，但該批 fixture 不含弱形式編號的真實長篇）。

剩餘已知限制：當一份文件確實以 `（一）（二）` 編號，而正文中又出現序列內的列舉行（例如章節 `（一）` 與 `（二）` 之間有一行 `（二）這是正文列舉`），兩者無法區分。這是該記法本身的歧義，`needsReview` 與匯入覆核流程是既有的補救途徑。
