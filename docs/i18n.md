# 介面語言（繁體／簡體）

dev-plan §15 要求「網站介面語言與正文顯示模式分開」。這份文件說明介面語言的實作；
正文的原文／繁體／簡體仍由 `apps/web/src/reader/conversion.ts` 處理（ADR-07），兩者互不影響。

- 介面語言：`zh-Hant`（預設）、`zh-Hans`。存在 `localStorage` 的 `ebook:ui-locale`。
- 正文繁簡：閱讀設定裡的「內文繁簡」，存在 reader settings，登入後同步到帳號。

## 使用方式

```ts
import { t } from '../i18n/translate.ts';

t('目錄')                                   // 繁體原字串就是 key
t('共 {n} 章', { n: 12 })                   // 佔位符讓數字留在句中
```

- `t` 是普通函式，不是 hook，所以 module-level 常數與非元件 helper 都能呼叫。
- **但 module-level 常數本身不要翻譯**：常數只在 import 時求值一次，翻譯會被凍結在
  啟動時的語言。慣例是常數存繁體原字串，在 render 位置才 `t(label)`。
  `lib/format.ts` 的 `typeLabel()` 等改成函式就是這個原因。
- 切語言靠 `I18nRoot` 的 state：它在整棵樹之上，樹內沒有 memo，所以一次 setState 會
  讓每個畫面重新 render 成新語言。用 `key` remount 也可以，但會丟掉捲動位置、
  開著的 sheet 與填了一半的表單。

## 翻譯怎麼來

`zh-Hant` 直接回傳原字串，零成本、不載入任何東西。

`zh-Hans` 的流程是：`i18n/vocabulary.ts` 的詞彙替換 → opencc 字元轉換。

需要詞彙表的原因是 opencc-js 在 `from: 't'` 下**只轉字元、不套詞組字典**：
設定→设定、搜尋→搜寻 都看得懂但不是簡體使用者預期的按鈕字；工具列、介面、伺服器
原字不變；暱稱更會變成非詞的「暱称」。所以詞彙表先把這些詞換成簡體寫法
（已驗證過 opencc 不會再動它們，見 `i18n/translate.test.ts`），其餘交給 opencc。

轉換器用 `opencc-js/t2cn` 單向 build（約 107 KB，完整 bundle 是 1.2 MB），
只在使用者實際選簡體時才下載；載完才切 state，所以不會先閃一格繁體。
載入失敗時 `t()` 回退成繁體原字串——降級，不是空白按鈕。

## 加語言的時候

同屬中文字形才適用上面的機械轉換。要加英文之類的語言，接縫在
`i18n/translate.ts` 的 `OVERRIDES`：轉換器之前先查的 per-locale 字典。
那時才需要真正的翻譯檔，而且要為現有約 500 條字串建 key。
現在不預先付這個成本：漏掉 `t()` 的字串會顯示繁體（可用），
而不是顯示 `reader.toc.title`（壞掉）。

## 範圍

- 翻譯的是**介面**：按鈕、標籤、提示、錯誤訊息、頁面 title 與 og 標記。
- 不翻譯**資料**：作品名、作者、章名、書籤備註、分類／標籤名稱。
  這些是內容，不是 UI；要轉繁簡的是閱讀頁的「內文繁簡」。
- 語言切換器在兩處：非閱讀頁面的 footer（`components/AppFooter.tsx`），
  以及閱讀設定 sheet 的「語言」列（閱讀頁沒有全站 chrome）。
- 介面語言只存在這台裝置，不同步到帳號——它跟瀏覽器語言設定同一性質。

## 偵測

有存過選擇就用存的。否則看 `navigator.languages`：只有明確的簡體標記
（`zh-Hans`、`zh-CN`、`zh-SG`、`zh-MY`）才切簡體。單純 `zh` 不算——它只說讀中文、
沒說字形，而這個站的內容是繁體，猜錯的代價比不猜大。
`<html lang>` 跟著切，因為字體選擇與螢幕閱讀器發音都靠它。
